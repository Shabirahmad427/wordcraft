# DOCX preservation contract and verification

## Phase 6C table-edit audit

WordCraft's existing table model and commands support row/column insertion and deletion, cell
merge/split, table/cell borders and shading, row heights, grid widths, repeated headers, row
splitting across pages, captions, and existing SEQ/REF caption references. The layout engine also
handles nested tables and reports table overflow. Charts can be rendered from cached values but
are preservation-only; SmartArt uses its saved drawing, and neither has a safe data-edit path.
Editing a nearby worksheet/table does not update an embedded chart workbook, so the original chart
package graph remains opaque and preserved.

Cell splitting now apportions a wide merged cell's existing grid columns across the requested
cells in reading order and retains its content only in the first result. A DOCX write/read
regression checks the resulting spans and widths. Splitting a vertically merged cell is rejected
because the current command edits only one row and cannot safely update the matching vertical
merge chain. This is an internal synthetic regression, not a Word-produced visual comparison.

## Earlier chart audit from 199822f

Existing implementations already cover custom XML/bibliography package graphs, complex citation fields (including Zotero/Mendeley field instructions), OMML equations, footnotes, tables, lists, sections, headers/footers, tracked changes, atomic saves and complete native recovery archives. Those implementations are reused. They do not establish lossless preservation of arbitrary OOXML.

## Chart preservation

Chart drawings use the existing opaque inline-object model. Their drawing markup is canonicalized, relationship IDs are rebound in the containing story, and drawing object IDs are regenerated uniquely. Inline and anchored chart drawing markup is retained for DOCX output; WordCraft layout does not reproduce chart positioning or appearance.

The existing bounded custom XML dependency traversal now also preserves chart graphs. Chart XML, dependent styles, embedded workbooks and dependent relationship files retain their exact imported bytes, part names and content types. External relationships are retained without fetching their targets. Unsupported extension markup inside these copied parts is retained unchanged. This is a part preservation promise, not byte identity of the entire ZIP or original drawing markup. In the later guarded package path below, original drawing markup and IDs remain unchanged instead of being regenerated.

Limits: 512 parts/relationships, 64 MiB preserved graph data, 128 KiB bookkeeping and 1 MiB per drawing, with a 16,384-node drawing bound. Missing dependencies/content types, corrupt ZIP entries, ambiguous case-insensitive ZIP names, malformed relationship records, unknown drawing namespaces, unsupported drawing types and generated-part collisions cause explicit errors on the checked paths. Failure during save leaves the original file and live document metadata unchanged. Markup-compatibility attributes within chart drawings are rejected when namespace canonicalization cannot safely retain their meaning.

`file.open`, `file.save` and `file.info` expose `compatibilityWarnings`; the desktop File → Info page displays them. Standard bar/column, line, area, pie, doughnut and scatter charts are drawn from cached chart data. The chart object model stores drawing primitives and the original package graph, not editable series data. Chart caches and embedded workbooks are preserved on DOCX saves. The constrained **Edit Chart Data** workflow can update only validated chart families and embedded workbook ranges described below; edits to nearby worksheet-like tables do not update chart data. Unsupported or nonstandard charts remain read-only or placeholders. SmartArt uses its saved drawing and is not editable. OLE objects remain pictures in the editor, while their embedded or linked payload and picture parts are retained on DOCX save; they are not executed or opened. Unknown or unsafe package structures still use the guarded-preservation path or fail explicitly. Other export formats may lose chart, diagram or OLE package data. Existing macro behavior is unchanged; synthetic round-trip fixtures cover DOCX, DOTX and DOCM.

### Chart data editing status (Phases 6C.2–6C.3)

Selecting an embedded chart exposes **Chart Design → Edit Chart Data** and the same action in the chart context menu. The spreadsheet-like dialog shows each validated series name. Category/value charts show category labels and numeric values; supported scatter charts show paired numeric X/Y columns. Numeric cells reject empty, non-numeric and non-finite values, and scatter pairs must keep equal lengths. Tab follows the normal egui text-field focus order. Apply submits all series through the existing `chart.editData` command; this remains the only mutation path. It is one Undo/redo operation, refreshes chart rendering immediately, and its state is included by the existing recovery and atomic save paths. Cancel only discards the dialog draft.

The same dialog can edit an existing chart title and existing physical horizontal/vertical axis titles when each is represented as one rich-text run with one text node. Updates replace only that text node, retaining run properties and surrounding title XML, and are included in the same guarded transaction as chart data, Undo/redo, recovery and save. Physical axis roles are resolved from chart axis IDs and `axPos`, so horizontal bar charts map category/value axes according to their displayed orientation. Pie and doughnut charts have no axis-title fields. Formatting-only changes do not rewrite embedded XLSX parts. Missing titles cannot yet be added or removed, and multi-run, formula-linked, duplicated/ambiguous-axis or complex title structures remain read-only. WordCraft currently imports title text but does not paint axis-title text in its chart preview; title editing is therefore preserved in DOCX but not fully visible in the preview. These behaviors are verified with synthetic OOXML fixtures only; Microsoft Word/Excel interoperability has not been independently tested.

Inspection is read-only through `chart.inspectData`. A selected chart whose package, workbook or ranges do not pass the mapper opens as read-only and displays the engine diagnostic; no guessed values are made editable. Both commands require the open `documentId` and chart part. The dialog also submits its original validated snapshot; if the chart changes while it is open, the engine rejects the stale draft before making any change. The engine checks that the part belongs to that document, and `chart.editData` rebuilds and revalidates the package mapping before applying a transaction. Category/value example: `{"documentId": 3, "chartPart": "word/charts/chart1.xml", "series": [{"name": "Measurements", "categories": ["A", "B"], "values": [12, 18]}]}`. Scatter example: `{"documentId": 3, "chartPart": "word/charts/chart1.xml", "series": [{"name": "Measurements", "xValues": [1.5, 2.5], "values": [12, 18]}]}`. Omitted properties remain unchanged.

#### Scatter chart editing limits

The editable scatter subset requires a conventional `c:scatterChart` with one or more series. Each series name, X dataset and Y dataset must resolve to contiguous, single-column A1 ranges on the same worksheet in an embedded XLSX package. X/Y ranges must be nonempty and equal in length, contain finite numeric worksheet values, and use cells disjoint from every other mapped source (including series-name cells). The corresponding chart numeric caches must agree with the workbook's values and point order before editing. An edit writes only the mapped X/Y cache values and exact workbook cells, validates the rebuilt DOCX/XLSX packages, and confirms the caches and workbook still agree. The package digest and fresh mapping prevent stale transactions.

Formula-driven worksheet cells, external workbooks/links, formulas or noncontiguous/multi-column ranges, mismatched or sparse caches, overlapping cell references, malformed/missing worksheet structures, extension markup, macros, and other unsupported chart/package forms remain read-only with a diagnostic. There is no formula recalculation or chart-family conversion. Synthetic fixtures verify single- and multi-series mapping, transaction rejection, rendering refresh, Undo/redo, recovery, save/reopen and unrelated package preservation. No Microsoft Word or Excel application was used for independent interoperability verification.

The ordinary document-save preservation path still rejects unvalidated opaque chart/workbook changes. The engine command first serializes the current guarded editor projection, runs the immutable package transaction, then re-imports its fully validated result. That import refreshes rendered chart primitives and installs the synchronized chart/workbook parts as the new guarded save baseline; normal atomic file saving then writes them through the existing preservation path. The original file is not written by the chart command. The synthetic corpus fixture deliberately includes an external chart link and extension markup and is not evidence that such a chart is editable.

#### Read-only chart-to-workbook mapping subset

The internal `chart_mapping` API classifies a chart as mappable, unsupported, ambiguous, or inconsistent and returns value-only cell mappings. It accepts one embedded XLSX relationship, one simple bar, column, line, area, pie or doughnut chart, and one or more mapped series whose name is one string-reference cell, categories are a contiguous single-column string-reference range, and values are a same-length contiguous single-column numeric-reference range. Pie and doughnut are limited to exactly one series. Horizontal (`barDir="bar"`) and vertical (`barDir="col"`) bars are retained and reported distinctly. Line, area, pie and doughnut charts use the same mapped category/value structure. Absolute A1 references and quoted worksheet names are supported. Workbook sheet relationships are resolved before reading cells. Shared-string cells (including rich-text runs), inline strings, and numeric cells are read; exact worksheet part paths, sheet names, cell addresses, and values are returned. Every category/name/value cache must have sequential points and match the source cells in both type and value. Numeric category references are not supported.

External chart/workbook relationships, external-link data, formulas anywhere in the referenced worksheet, missing chart/workbook/sheet relationships, missing cells, unsafe targets, duplicate sheet names/cells, unsupported worksheet relationships, noncontiguous or multi-column ranges, extensions, multiple chart types, unsupported chart families/directions, unsupported cached-reference types, and cache length/value/type mismatches are rejected with a diagnostic. The mapper returns copied values only. `chart.editData` uses a fresh mapping for each synchronous operation and the transaction rechecks the package digest, relationships, cell mappings and cache consistency before and after modification. This is format-level internal verification over synthetic OOXML only, not Microsoft Excel or Word interoperability verification.

#### Internal atomic chart transaction foundation

An internal package transaction now accepts a fresh validated plan and per-series changes for names, category labels, and numeric values. A plan is bound to the exact original DOCX byte stream by a SHA-256 digest and records the mapped chart/workbook parts. Immediately before editing, the transaction checks the digest, validates the DOCX package, resolves the chart-to-workbook relationship again, and re-runs the read-only mapper; changed source cells or relationships make the plan stale. All chart cache and XLSX changes are staged in memory. Only after both parts are spliced, the DOCX and nested XLSX reopen successfully, and the chart mapper confirms the requested values does the API return a replacement package. The input slice is immutable, and any error returns no output package.

The transaction supports the same simple embedded bar/column/line/area/single-series pie/doughnut chart subset as the mapper, including horizontal and vertical bar orientation. It edits mapped numeric cells, plain inline text cells, simple shared-string entries, and their corresponding chart cache points. Shared-string items are updated only when every workbook cell referencing that item is part of the same transaction and requests the same replacement; rich-text shared/inline cells, comments/CDATA/processing instructions inside target values, formula-driven cells, external links, unsupported ranges/structures, conflicting repeated-cell edits, non-finite numeric values, stale plans, missing relationships, and mismatched caches fail safely. Unknown XML markup and attributes outside the exact edited text spans remain byte-for-byte untouched. The outer DOCX package is rebuilt, so ZIP container bytes/compression metadata can differ even though every unmodified uncompressed part is retained byte-for-byte. The only modified outer DOCX parts are the mapped chart XML and embedded workbook ZIP; within the XLSX, only referenced worksheet values and, where safe, shared-string text are changed.

The transaction is integrated into the engine without a graphical editor. A successful command replaces the session's imported document model in one mutating command, so Undo and redo restore the prior/current document and guarded package baseline together. Recovery stores the synchronized chart/workbook parts in the model and retains the exact initially opened package independently. Re-import refreshes rendering from updated chart caches. Saving uses the existing guarded and atomic DOCX path; failed transactions or failed saves leave the prior session/package or destination file unchanged. Engine regressions cover multiple edits, undo/redo, recovery, rendering, save/reopen, unsupported/stale requests, unrelated uncompressed parts and failed saves. These tests use synthetic OOXML and do not verify rendering in Microsoft Word or Excel.

#### Safe chart legend formatting

The existing chart-data dialog can change an explicitly stored legend position among left, right, top and bottom for the same seven validated chart families: horizontal/vertical bar, line, area, single-series pie/doughnut and scatter. The position change uses `chart.editData` and is combined with series edits as one Undo operation. Formatting-only changes splice the existing `c:legendPos/@val` attribute and leave the embedded XLSX bytes untouched. Charts with a missing, duplicate or unsupported legend position remain read-only for this property; WordCraft does not add a legend, alter other legend formatting, or edit titles, axes, number formats, data labels, colors or line styles in this increment. Synthetic package, dialog and engine regressions cover the implementation; independent Microsoft Word/Excel rendering comparison has not been performed.

Undo and recovery retain the opaque object and graph bytes. Recovery holds the current edited package parts in the model and retains the exact initially opened package independently. Removing a chart can leave preserved orphan parts in that save; preservation does not synchronize embedded workbook data with edits to nearby tables. Graphs shared with regenerated document parts, or colliding with custom XML graph output, can be rejected rather than rewritten unsafely.

## Automated compatibility corpus

The corpus is generated from original Rust fixture code in `crates/docx/tests/common/charts.rs`; no proprietary documents or assets are committed. Scientific manuscript, thesis and tracked report variants combine charts and XLSX data with citation fields, bibliography settings, equations, footnotes, a table, nested numbering, a header, PAGE footer, caption cross-reference and tracked insertion. These are synthetic regressions, not certified Word-produced reference files.

Generate inspectable fixtures and run the package regressions:

```sh
WORDCRAFT_COMPAT_CORPUS_DIR=/tmp/wordcraft-compatibility-corpus cargo test -p wordcraft-docx --test charts
cargo test -p wordcraft-engine --test opaque_charts
cargo xtask ci
cargo build --release -p wordcraft -p wordcraft-cli
```

Six package integration tests exercise three generations and multiple output flavors, body/header relationship scopes, unique drawing IDs, missing/corrupt/unsafe dependencies and rejected exports. Two engine tests cover edit/save/reopen, Undo, recovery restoration, failed-save integrity and multi-page layout/raster self-comparison. Two unit tests cover corrupt secondary ZIP data, ambiguous package names and hostile drawing/bookkeeping limits. All six CI checks passed with **831 tests**, including **10 new tests** in this arc.

The pixel comparison is WordCraft before/after restoration and round-tripping, not a Microsoft Word reference comparison. Linux verification does not establish native Windows/macOS behavior. Independent Word reference outputs and a consented real-world corpus are unavailable in this environment. There is no full Microsoft Word 365 parity claim.

## Package-wide safety audit from 6807535

At 6807535, custom XML and chart graphs were retained but the main exporter still regenerated modeled XML. Content controls were flattened; OLE/ActiveX/unknown relationships, unreferenced embedded parts, unknown styles/settings/numbering properties and extension metadata could disappear. SmartArt drawing types caused an explicit import error. A controlled synthetic probe run through the installed 6807535 CLI lost **14 package parts**, plus the SDT wrapper and its data binding. The probe omitted its SmartArt drawing solely to reach the older export path; its original dependency parts were still present.

The new package-wide path retains the exact source ZIP, its bounded editor projection and native export baseline in Arc-backed `Document.passthrough`. The chart/custom XML mechanisms remain separate and run first. No lower layer depends on UI code and no dependency was added. Undo, recovery and atomic saves reuse their existing implementations.

A complete source/native package comparison checks entry names, expanded XML names, all attributes (including namespace declarations), text and tree structure; comments, processing instructions and declaration differences require preservation. Unmodeled package data therefore selects guarded mode rather than being overwritten with regenerated XML. Imported macro/ActiveX/signature-sensitive packages also select guarded mode even when the ordinary writer can reproduce them. A package with a blocked native export remains recoverable but its ordinary save fails explicitly.

### Preservation and supported edits

Guarded no-op saves in the original Word package flavor return the exact imported ZIP bytes. Tested main-body text edits splice only proven text ranges in the original story bytes. Every other part, original relationship ID/target, content type, namespace declaration, extension attribute, custom XML binding, SDT metadata, unknown property and embedded payload stays unchanged. SmartArt, OLE and ActiveX data are retained as **inert bytes**, without executing code or fetching external targets. Disconnected parts and nested/cyclic relationship graphs are retained too. Some unsupported drawings show placeholders; preservation does not imply rendering or editing support.

Only isolated text edits in the first simple text run of a directly mapped body paragraph are currently supported in guarded mode. The model, run formatting, objects, properties and all other document state must match the original projection after accounting for those edits. Mapping follows source block position, so identical text inside a bound control cannot redirect an edit to an ordinary paragraph. Content-control/custom XML/revision wrappers are protected; ambiguous mappings, formatting boundaries, tables, header/footer edits, object changes and structural edits fail explicitly. Source XML in UTF-16 is retained, but text splicing in it is refused. Unchanged field markup is retained, including a pre-existing malformed field range, rather than silently repaired.

Ordinary formatting and structural editing remain available for reproducible native packages. Guarded mode is deliberately conservative: normalization differences or added generated parts can select it even when no user-visible unsupported object is apparent. It is a safety fallback, not a general OOXML merge engine.

Original core metadata and application statistics remain byte-exact in guarded packages. File Save defers automatic timestamps, revision increments and last-modified-by updates; statistics may be stale. Explicit metadata/style/numbering/settings edits currently fail in guarded mode. DOCX/template flavor changes update only a uniquely identified main content type while retaining extension attributes. Guarded macro-enabled packages cannot be converted to macro-free flavors by discarding active content. OPC-signed packages reject text/flavor changes that would invalidate a signature. Signature cryptography is not verified.

### Checked input and storage limits

All imported package parts and supported XML content types are inspected before the lenient model reader. Checks cover duplicate/ambiguous ZIP names, corrupt or unreadable entries, strict XML well-formedness, bound namespace prefixes, duplicate expanded attributes, forbidden XML characters, unsupported encodings and DTD rejection. Content types must exist and have nonconflicting definitions. All relationship parts—including orphan graphs—must have existing owners, complete unique IDs, valid target modes and existing internal dependencies. Office relationship-namespace attributes, including SmartArt `r:dm/lo/qs/cs`, must resolve within their containing part. Package escape targets are rejected. External targets remain untouched and unfetched.

Limits now apply to imported DOCX packages: **512 parts and 64 MiB total decompressed data**, with 64 MiB per-part/retained ZIP budgets, **16 MiB per XML inspection and model snapshot**, 200,000 XML elements per part and depth 256. This replaces the older permissive 256/512 MiB import bounds. Legitimate files above these limits fail explicitly. URI-escaped/nonstandard part names and unsupported encodings may also fail. Embedded binary formats are not recursively interpreted or schema-validated. DTD-bearing custom XML is rejected, not sanitized. This is structural/graph validation, not a complete OOXML schema validator or malware scanner.

Recovery retains the editor model, all preservation state and the independent original package copy. Failed saves keep the original file, document metadata/path and dirty state unchanged. An unsupported edit can still be recovered even if it cannot yet be exported safely to DOCX. Removing or corrupting a preservation-state entry produces an error rather than disabling the guard.
